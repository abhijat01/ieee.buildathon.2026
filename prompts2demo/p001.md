## Task: Write a User Story — Add Project or Professional Experience

You are a senior business analyst and product owner working on a Resume Builder application.

Write a detailed, implementation-ready user story, including acceptance criteria, for the following feature.

### Feature: Add Project or Professional Experience Using AI

A user should be able to add a project or professional experience to their resume database by typing or pasting a free-form description.

The user should not need to manually enter each field. Instead, the system will use an LLM to extract structured information from the description.

### Functional Requirements

**1. Enter Experience**

- Provide a text area where the user can type or paste a description of a project or professional experience.
- Provide an "Analyze" button.
- The input may contain unstructured text, multiple sentences, or bullet points.

**2. AI-Based Extraction**

When the user clicks Analyze, the backend should call an LLM to extract:

- Experience type: Project or Professional Experience
- Project name or title
- Company or organization name
- Start date
- End date
- Description

The LLM integration MUST:

- Use a typed API call with a strongly typed response object.
- Define and enforce a JSON schema for the LLM response, using the provider's structured-output capability.
- Deserialize the response into a typed DTO and validate it on the backend.
- Never rely on parsing arbitrary natural-language responses or extracting JSON from Markdown.
- Return null for information that cannot be confidently identified.
- Never invent missing dates, company names, or project names.
- Preserve partial dates when only a year or month/year is provided.
- Support ongoing experiences where an end date is not available.

**3. Preview Before Saving**

After extraction, show the user a preview containing all extracted fields.

- The preview must be editable so the user can correct AI extraction errors.
- Display missing values clearly.
- Provide "Accept & Save" and "Cancel" options.
- Do not save anything to the database during the extraction or preview steps.
- Only save the experience after the user explicitly accepts the preview.
- Save the user-reviewed values, not the original unreviewed LLM output.

**4. Persistence**

Once accepted, save the structured experience in the application's database.

The application should retain the original user-entered text alongside the structured information for traceability.

**5. Error Handling**

Define expected behavior for:

- Empty input
- Invalid or ambiguous dates
- Missing company or project name
- LLM API failures
- Invalid structured responses
- Database failures

### Deliverables

Produce:

1. A concise feature description.
2. One primary user story in standard "As a / I want / So that" format.
3. Acceptance criteria in Given/When/Then format.
4. Business rules and validation requirements.
5. A proposed typed extraction response schema, including appropriate types, nullability, and date precision.
6. A list of relevant test scenarios, including edge cases.
7. Explicit assumptions and open questions, if any.

### Constraints

- Keep the feature small enough to implement and demonstrate during a live software engineering workshop.
- Do not introduce unnecessary capabilities such as authentication, resume generation, or job matching.
- Do not write implementation code yet.
- Do not implement the feature until the user story and acceptance criteria have been reviewed and approved.

The output should be clear enough that a software engineer or AI coding agent can implement the feature without having to reinterpret the requirements.
